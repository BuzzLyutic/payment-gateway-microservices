# ADR-003: NATS JetStream как брокер сообщений

## Статус
Accepted

## Контекст

Событийная архитектура платформы (ADR-001) требует надёжного брокера сообщений с персистентностью и гарантией доставки. Базовый NATS Core — fire-and-forget: если consumer недоступен в момент публикации или падает во время обработки, сообщение теряется навсегда. Для платёжной платформы это неприемлемо: потеря события PaymentCreated или PaymentRiskApproved — это прямые финансовые потери и нарушение целостности данных.

Требования к брокеру:

- Персистентность. События сохраняются независимо от состояния consumers;
- At-least-once доставка. Сообщение доставляется повторно при сбое;
- Семантика очереди. Каждое событие обрабатывается ровно одним сервисом;
- Минимальная операционная сложность. Платформа разворачивается одной командой docker-compose up.

## Решение

Принят NATS JetStream — встроенный в NATS persistence layer и stream processing engine. JetStream превращает NATS из best-effort в полноценную messaging platform с персистентностью, сохраняя при этом минимальную операционную сложность базового NATS.

**Конфигурация стрима PAYMENTS:**

```go
js.CreateOrUpdateStream(ctx, jetstream.StreamConfig{
    Name: "PAYMENTS",
    Subjects: []string{
        "payment.created",
        "payment.risk_approved",
        "payment.risk_blocked",
        "payment.completed",
    },
    Storage:   jetstream.FileStorage,
    Retention: jetstream.WorkQueuePolicy,
    MaxAge:    72 * time.Hour,
})
```
**WorkQueuePolicy** — ключевое решение. Сообщение удаляется из стрима сразу после того, как один consumer его подтвердил. Это реализует семантику очереди задач - каждое событие обрабатывается ровно одним сервисом, хранить обработанное событие бессмысленно.

## Сравнение политик удержания

Политика |	Удаление |	Семантика |	Применение |
--- | --- | --- | --- |
LimitsPolicy |	По лимитам (размер, возраст) |	Храни сколько задано |	Логи, аналитика
InterestPolicy |	Когда все consumers ackнули |	Fan-out |	Broadcast событий
WorkQueuePolicy| 	Как только один consumer ackнул |	Queue |	Обработка задач

> MaxAge: 72h — страховка: если событие не забрали за 3 дня (все consumers недоступны), оно удаляется автоматически.
Бесконечное накопление необработанных событий не менее опасно, чем
их потеря.

**AckExplicitPolicy** и момент подтверждения — второе ключевое решение.

AckExplicitPolicy означает, что сервер не считает сообщение обработанным до явного msg.Ack(). Никаких автоматических подтверждений.

**Правильная последовательность обработки:**

1. Получить сообщение;
2. Выполнить бизнес-логику (запись в БД, публикация новых событий);
3. Только при успехе - msg.Ack();
4. При ошибке - msg.Nak() (redelivery) или msg.Term() (poison message).

**Критичность для платёжной платформы:**

Ack сразу после получения припадении во время записи в БД — событие исчезает из стрима (WorkQueuePolicy), платёж теряется. Ack после успешной бизнес-логики в сочетании с idempotency key даёт effectively-once семантику без XA-транзакций.

**Персистентность даёт платёжной платформе три важных свойства:**

- Устойчивость к сбоям. Сервис упал — события ждут на диске, после восстановления обработка продолжается с того места где остановилась;
- Replay. При обнаружении бага или необходимости отката можно переиграть события за нужный период;
- Аудит. Последовательность событий по каждому платежу сохранена и доступна для проверки — важно для compliance.

## Альтернативы

### Apache Kafka

Наиболее популярное production-решение для событийных систем. Богатая экосистема, широкая востребованность на рынке труда, развитые инструменты для stream processing (Kafka Streams, ksqlDB).

Отвергнут по следующим причинам:

- Операционная сложность. До версии 3.x требует ZooKeeper — отдельный кластер для координации. KRaft (встроенный консенсус) доступен, но добавляет сложность настройки;

- Потребление ресурсов. JVM-based: минимальное потребление памяти от 1 ГБ против ~50 МБ у NATS. Для локальной разработки и умеренной нагрузки это существенно;

- Несоответствие масштабу. Kafka оправдана при объёмах от миллионов сообщений в секунду. Производительность NATS JetStream (микросекундная латентность) достаточна для данного проекта с запасом.

Kafka остаётся правильным выбором при необходимости consumer groups с независимыми offsetами, log compaction или интеграции с экосистемой Confluent.

### RabbitMQ

Зрелое решение с гибкой моделью routing (exchanges, bindings, routing keys). Проще Kafka в операционном плане.

Отвергнут: потребление ресурсов выше NATS (~200 МБ против ~50 МБ), нативная Go-интеграция слабее, дополнительная концептуальная сложность модели exchanges/queues/bindings без выигрыша для данного use case.

### NATS Core (без JetStream)

Минимальная сложность, максимальная производительность. Достаточен для сценариев без требований к персистентности.

Отвергнут: fire-and-forget семантика неприемлема для платёжной платформы. Потеря события при временной недоступности consumer — это потеря информации о транзакции без возможности восстановления.

## Последствия

### Стало лучше:

- Единственный бинарь без внешних зависимостей: nats-server -js запускает полноценный персистентный брокер
- ~50 МБ RAM против 1+ ГБ у Kafka — вся платформа комфортно работает на локальной машине
- At-least-once доставка с effectively-once семантикой через AckExplicit + idempotency key
- Мониторинг через встроенный HTTP endpoint (:8222) без дополнительных инструментов

### Принятые ограничения:

- NATS JetStream менее распространён чем Kafka — меньше готовых коннекторов, меньше экспертизы на рынке. При необходимости интеграции с внешними системами (Spark, Flink, Elasticsearch) потребуется разработка кастомных коннекторов.

- WorkQueuePolicy с одним стримом PAYMENTS означает что все subject'ы разделяют одно хранилище и одни лимиты. При существенном росте нагрузки отдельные subject'ы потребуют выделения в независимые стримы для изоляции и независимого масштабирования.
