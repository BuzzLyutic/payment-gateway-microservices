# ADR-001: Event-Driven Architecture через NATS JetStream

## Статус
Accepted

## Контекст

Платформа агрегации платёжных провайдеров состоит из четырёх независимых
микросервисов: API Gateway, Transaction Service, Risk Service, Provider Service.
При проектировании межсервисного взаимодействия рассматривались два подхода:
синхронные HTTP вызовы и асинхронная событийная архитектура.

Платёжная платформа накладывает жёсткие требования:
- Потеря данных о транзакции недопустима
- Сбой одного сервиса не должен останавливать обработку остальных
- Время отклика для клиента должно быть минимальным

При синхронной модели клиент ждёт ответа на протяжении всей цепочки. Это создаёт несколько критических проблем:

**Время отклика.** Клиент блокирован до завершения обработки. Суммарная латентность складывается из времени работы каждого сервиса и каждого сетевого вызова. Для платёжной платформы с оценкой рисков и внешними провайдерами это неприемлемо.

**Каскадные отказы.** Сетевые вызовы всегда сопряжены со сбоями. При синхронной цепочке из N сервисов вероятность успеха равна произведению вероятностей успеха каждого звена. Обрыв в любом месте цепочки — клиент получает ошибку после ожидания.

**Связанность сервисов.** При синхронных вызовах каждый сервис должен знать адрес следующего. Временная недоступность любого сервиса требует немедленной обработки вышестоящим — усложняет логику retry и circuit breaking.

**Восстановление после сбоев.** Если сервис упал в середине обработки,
контекст теряется. При синхронной модели восстановить обработку без
повторного запроса от клиента невозможно.

## Решение

Принята событийно-ориентированная архитектура (EDA) с паттерном Saga Choreography. Сервисы взаимодействуют исключительно через NATS JetStream, публикуя и потребляя события.

Поток обработки платежа через события:

    payment.created      → Risk Service оценивает риски
    payment.risk_approved → Provider Service маршрутизирует платёж
    payment.completed    → Transaction Service обновляет статус

API Gateway возвращает клиенту ответ `pending` немедленно после записи транзакции — клиент не ждёт обработки.

Каждый сервис:
- подписан только на нужные ему события
- не знает об адресах других сервисов
- подтверждает обработку (Ack) только после успешного завершения
  бизнес-логики

## Альтернативы

**Синхронные HTTP вызовы (REST/gRPC)**

Рассматривались как baseline. Отвергнуты по причинам описанным в разделе
Контекст: блокирующее ожидание клиента, каскадные отказы, потеря контекста при сбоях.

Для health check и получения статуса транзакции синхронный HTTP оставлен как единственно разумный выбор — клиент запрашивает конкретные данные и ожидает немедленного ответа.

**Apache Kafka**

Рассматривался как наиболее популярное production-решение для событийных систем. Обладает богатой экосистемой, широко востребован на рынке труда.

Отвергнут по следующим причинам:
- Требует ZooKeeper (до версии 3.x KRaft) или отдельного управления
  кластером — существенно увеличивает операционную сложность
- JVM-based: потребление памяти от 1 ГБ против ~50 МБ у NATS
- Время настройки и отладки кратно выше
- Производительность Kafka оправдана при объёмах от миллионов сообщений
  в секунду — избыточна для данного проекта

**RabbitMQ**

Зрелое решение с удобной моделью routing. Отвергнут: потребление ресурсов выше NATS (200 МБ против 50 МБ), операционная сложность выше, нативная интеграция с Go слабее.

## Последствия

**Стало лучше:**
- Клиент получает ответ немедленно — время отклика API не зависит от
  времени обработки провайдером
- Сбой любого сервиса не теряет данные — сообщения персистируются
  в JetStream и доставляются после восстановления
- Сервисы полностью независимы — можно деплоить, рестартовать,
  масштабировать каждый отдельно
- Добавление нового участника обработки не требует изменений
  существующих сервисов

**Стало сложнее:**
- Eventual consistency: статус транзакции обновляется не мгновенно,
  клиент должен опрашивать API или получать webhook
- Трассировка запроса через несколько событий сложнее чем стек вызовов
  в синхронной системе — требует correlation ID в каждом событии
- Тестирование интеграционных сценариев требует поднятого NATS,
  unit-тесты требуют мокирования publisher/consumer интерфейсов

**Принятые trade-offs:**
Выбрана модель Choreography (сервисы реагируют на события самостоятельно) вместо Orchestration (центральный координатор). Choreography даёт меньшую связанность, но усложняет отслеживание общего состояния саги. Для платформы с четырьмя сервисами и линейным потоком обработки это приемлемо.
