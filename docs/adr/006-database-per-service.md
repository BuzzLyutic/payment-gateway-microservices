# ADR-006: Database per Service

## Статус
Accepted

## Контекст

Платформа декомпозирована на четыре микросервиса с различной природой данных и различными требованиями к хранилищу:

**transaction-service** — бизнес-состояние платежа с точки зрения мерчанта. Данные долгоживущие, требуют ACID-гарантий, история изменений статусов критична для аудита.

**provider-service** — техническая интеграция с платёжными провайдерами. Своя модель данных: конфигурации провайдеров, параметры Beta-распределения, Thompson Sampling, статистика маршрутизации. Меняется чаще — новые провайдеры, изменения API, compliance-требования.

**risk-service** — оценка рисков. Данные короткоживущие: velocity-счётчики нужны только в пределах временного окна, после принятия решения результат сохраняется в transaction-service.

**api-gateway** — stateless прокси с rate limiting и аутентификацией. Оперативные данные: счётчики запросов, API-ключи, сессии.

При проектировании стоял выбор: одна общая БД или изолированные хранилища для каждого сервиса.

## Решение

Принят паттерн Database per Service. Каждый сервис владеет собственным хранилищем и не имеет прямого доступа к данным других сервисов.

**Два экземпляра PostgreSQL:**

- `postgres` — для transaction-service
- `postgres-provider` — для provider-service

**Redis** — для risk-service (velocity-счётчики) и api-gateway (rate limiting, API-ключи).

Межсервисное взаимодействие — исключительно через события NATS JetStream
(ADR-001). Прямых SQL-запросов между сервисами нет.


**Почему Redis для risk-service и api-gateway:**

Природа данных принципиально иная — оперативная, короткоживущая.

- Risk Service: velocity-счётчики существуют только в пределах временного окна (10 минут). Redis INCR + TTL — нативный инструмент для этой задачи. После принятия решения данные можно выбросить — результат сохраняется в transaction-service. Постоянное хранение избыточно.

- API Gateway: rate limiting (sliding window через INCR), аутентификация (хэши API-ключей), конфигурации мерчантов — классические use-case'ы для Redis. Все эти данные либо вычисляемые (счётчики), либо кэшируемые (конфигурации). Критическое состояние всё равно живёт в transactional сервисах.

Redis здесь выступает как оперативная память системы, PostgreSQL — как постоянная запись.

## Альтернативы

**Единая PostgreSQL с разными схемами**

Один экземпляр БД, данные разделены по схемам (`transaction.*`, `provider.*`) или префиксам таблиц.

Привлекательность: проще в управлении на старте, возможность SQL JOIN между сервисами, меньше инфраструктуры, быстрее разработка MVP.

Отвергнут по следующим причинам:

- *Операционные риски.* Тяжёлый аналитический запрос или неосторожная миграция в provider-service создают нагрузку на shared CPU и I/O, влияя на transaction-service. В платёжных системах деградация core transaction processing недопустима.

- *Связанность развёртывания.* Миграции схемы одного сервиса требуют координации со всеми командами. Provider-service меняется чаще (новые провайдеры, изменения API) — при общей БД это блокер для независимого деплоя.

- *Нарушение границ контекстов.* Единая БД создаёт соблазн и техническую возможность писать запросы через границы сервисов. Через 8–12 месяцев это приводит к неявным зависимостям, которые сложно обнаружить и ещё сложнее разделить.

- *Compliance.* Provider-service работает с чувствительными данными. Изоляция на уровне БД упрощает аудит и контроль доступа — чётко понятно какой сервис имеет доступ к каким данным.

**Единая PostgreSQL + row-level security**

Одна БД с политиками безопасности на уровне строк для изоляции данных.

Отвергнут: решает проблему доступа, но не решает проблемы конкурентной нагрузки и связанности развёртывания. Операционная сложность row-level security выше чем просто два экземпляра PostgreSQL.

**PostgreSQL для всех сервисов включая risk и gateway**

Единообразие хранилища, не нужен Redis.

Отвергнут: velocity-проверки через SQL (`COUNT(*) WHERE created_at > NOW() - interval`) значительно медленнее Redis INCR + TTL. Rate limiting через SQL создаёт нагрузку на transactional БД на каждый входящий запрос. Redis решает эти задачи нативно и на порядки быстрее.

## Последствия

**Стало лучше:**

- Независимость развёртывания: миграции provider-service не затрагивают transaction-service. Каждый сервис деплоится, масштабируется и рестартует независимо.

- Изоляция отказов: деградация одной БД не влияет на другие сервисы. При падении postgres-provider транзакции продолжают создаваться и сохраняться в postgres.

- Соответствие инструмента задаче: PostgreSQL для долгосрочных ACID-данных, Redis для оперативных короткоживущих данных.

- Чёткое владение данными: каждая команда знает свою БД, границы ответственности очевидны.

**Стало сложнее:**

- Нет SQL JOIN через границы сервисов. Данные о транзакции и данные о провайдере объединяются на уровне приложения через события, а не на уровне БД через JOIN.

- Eventual consistency между сервисами. Статус транзакции в transaction-service и статистика провайдера в provider-service консистентны в конечном счёте, не мгновенно.

- Операционная нагрузка: два экземпляра PostgreSQL требуют раздельного мониторинга, backup и управления connection pools.

**Принятые trade-offs:**

Усложнение инфраструктуры на старте оправдано долгосрочными преимуществами независимости и изоляции. В платёжных системах цена ошибки высока — лучше принять небольшой инфраструктурный overhead сразу, чем мучительно делить монолитную БД при росте команды и нагрузки.
