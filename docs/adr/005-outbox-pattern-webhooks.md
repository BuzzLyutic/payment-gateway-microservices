# ADR-005: Outbox Pattern для гарантированной доставки webhook-уведомлений

## Статус
Accepted

## Контекст

Платёжная платформа обрабатывает транзакции асинхронно. Мерчант создаёт платёж и получает статус `pending` — финальный результат появляется позже. Мерчанту необходимо знать об изменении статуса: для обновления заказа, отправки товара, уведомления покупателя.

Без механизма уведомлений мерчант вынужден периодически опрашивать `GET /payments/{id}` — polling. Это создаёт избыточную нагрузку и задержку обнаружения результата, зависящую от интервала опроса.

Webhook решает проблему: платформа сама уведомляет мерчанта о результате через HTTP POST на зарегистрированный URL. Вопрос — как реализовать webhook с гарантией доставки.

### Проблема прямого HTTP вызова из consumer:

Наивная реализация: обновить статус в БД → отправить POST мерчанту.

Это создаёт два класса проблем:

**Потеря уведомления:**
```sql
UPDATE transactions SET status = 'captured' - ✓ сохранено в БД
``` 

`POST https://merchant.com/webhook` - ✗ сеть упала:

- статус обновлён, мерчант не уведомлён
- момент упущен, повторить невозможно


**Ложное уведомление:**
`POST https://merchant.com/webhook` - ✓ мерчант получил

```sql
UPDATE transactions SET status = 'captured' - ✗ БД недоступна
```
- мерчант думает что платёж прошёл
- в БД платформы статус не обновлён
- расхождение состояний


Прямой HTTP вызов нарушает атомарность: две операции (обновление статуса и отправка уведомления) выполняются независимо, любая из них может упасть.

Дополнительная проблема: webhook delivery зависит от внешней системы (сервер мерчанта). Недоступность мерчанта не должна влиять на бизнес-состояние платежа — статус платежа является истиной независимо от того, получил ли мерчант уведомление.

## Решение

Принят паттерн Transactional Outbox. Обновление статуса транзакции и создание записи о необходимости уведомления выполняются атомарно в одной DB-транзакции. Фоновый воркер независимо читает очередь и доставляет уведомления с retry.

**Схема данных:**

```sql
-- Конфигурация мерчантов: webhook URL и HMAC-секрет
CREATE TABLE merchants (
    id             VARCHAR(64) PRIMARY KEY,
    webhook_url    TEXT,
    webhook_secret VARCHAR(128),
    is_active      BOOLEAN NOT NULL DEFAULT true
);

-- Outbox-очередь доставки уведомлений
CREATE TABLE webhook_deliveries (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    transaction_id UUID NOT NULL REFERENCES transactions(id),
    merchant_id    VARCHAR(64) NOT NULL REFERENCES merchants(id),
    event_type     VARCHAR(64) NOT NULL,
    payload        JSONB NOT NULL,
    status         VARCHAR(20) NOT NULL DEFAULT 'pending',
    attempts       INTEGER NOT NULL DEFAULT 0,
    max_attempts   INTEGER NOT NULL DEFAULT 5,
    next_retry_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_error     TEXT,
    delivered_at   TIMESTAMPTZ,
    CONSTRAINT chk_status CHECK (status IN ('pending', 'delivered', 'failed'))
);

-- Partial index: только pending записи — воркер не читает delivered/failed
CREATE INDEX idx_webhook_deliveries_pending
    ON webhook_deliveries(next_retry_at)
    WHERE status = 'pending';
```

**Атомарная запись в consumer:**

```go

// BEGIN TRANSACTION
tx, _ := pool.Begin(ctx)

// 1. Обновляем статус транзакции
tx.Exec(ctx, "UPDATE transactions SET status = $2 WHERE id = $1", id, status)

// 2. Создаём запись в outbox — в той же транзакции
tx.QueryRow(ctx, "INSERT INTO webhook_deliveries (...) VALUES (...)", ...)

// COMMIT — оба действия атомарны
tx.Commit(ctx)
```

Если коммит не прошёл — ни статус не обновлён, ни запись в outbox не создана. Система остаётся консистентной.

**Отказ webhook delivery не прерывает транзакцию:**

- Статус платежа — это истина. Webhook — уведомление об этой истине.
- Платёж проведён независимо от того, получил ли мерчант уведомление.
- Нельзя откатывать уже проведённый платёж из-за недоступности сервера мерчанта.

```go

if err := webhookRepo.CreateDelivery(ctx, tx, delivery); err != nil {
    // Логируем, но не прерываем транзакцию
    slog.Error("failed to create webhook delivery, skipping", ...)
    // tx.Commit() выполнится — статус обновится в любом случае
}
```

**Воркер доставки с экспоненциальным backoff:**

Отдельный фоновый воркер читает pending записи из webhook_deliveries и доставляет HTTP POST на URL мерчанта.

```text

Попытка 1 → ошибка → следующая через 30 секунд
Попытка 2 → ошибка → следующая через 5 минут
Попытка 3 → ошибка → следующая через 30 минут
Попытка 4 → ошибка → следующая через 2 часа
Попытка 5 → ошибка → статус = failed
```

>FOR UPDATE SKIP LOCKED в запросе воркера — безопасен при нескольких
инстансах сервиса, исключает двойную доставку.

HMAC-SHA256 подпись каждого запроса:

```text
X-Webhook-Timestamp: 1714000000
X-Webhook-Signature: sha256=<hmac(secret, timestamp + "." + body)>
```

Мерчант верифицирует подпись, используя заранее выданный секрет. Это защищает от подделки webhook-запросов третьими сторонами.

## Альтернативы

### Прямой HTTP вызов из consumer

Проще в реализации — нет дополнительных таблиц и воркера.

Отвергнут: нарушает атомарность. При сбое сети после обновления статуса уведомление теряется безвозвратно. При сбое БД после отправки уведомления возникает расхождение состояний между платформой и мерчантом. Нет возможности retry.

### NATS как транспорт для webhook-событий

Публиковать webhook-событие в NATS, отдельный сервис доставляет его
мерчанту.

Отвергнут: добавляет ещё один hop и точку отказа. Проблема атомарности перемещается на уровень "обновить статус в БД + опубликовать в NATS" — те же два независимых действия. Решается через Transactional Outbox в любом случае.

### Change Data Capture (Debezium + Kafka Connect)

Отслеживать изменения в таблице transactions через WAL PostgreSQL,
генерировать webhook-события автоматически.

Отвергнут: существенно увеличивает операционную сложность — требует Kafka, Debezium, Kafka Connect. Избыточно для текущего масштаба. Является правильным выбором при необходимости интеграции с множеством внешних систем.

### In-memory очередь с персистентностью на диск

Локальная очередь в памяти процесса с периодическим сбросом на диск.

Отвергнут: при нескольких инстансах сервиса — независимые очереди, сложная координация. PostgreSQL уже присутствует в системе — использование его как надёжного хранилища очереди не добавляет новых зависимостей.

## Последствия

### Стало лучше:

- Атомарность гарантирована. Обновление статуса и создание записи о необходимости уведомления неразделимы. Невозможна ситуация когда статус обновлён, а уведомление потеряно — или наоборот.

- Надёжность доставки. Экспоненциальный backoff с 5 попытками охватывает временные сбои сети, перезапуски сервера мерчанта, кратковременные перегрузки.

- Независимость статуса платежа от внешних систем. Недоступность сервера мерчанта не влияет на бизнес-состояние транзакции.

- Мерчант имеет polling fallback. GET /payments/{id} доступен всегда как резервный способ получить актуальный статус.

### Стало сложнее:

- Два новых компонента: таблицы merchants и webhook_deliveries, фоновый воркер доставки. Увеличивается объём кода и количество движущихся частей.

- Eventually consistent доставка: мерчант получает уведомление не мгновенно, а в течение времени определяемого интервалом воркера (30 секунд по умолчанию). Для большинства сценариев приемлемо.

## Принятые ограничения:

- At-least-once семантика: при определённых сценариях сбоя (воркер упал после успешной доставки, но до MarkDelivered) возможна повторная доставка. Мерчант должен обеспечить идемпотентность обработки webhook по полю transaction_id.

- При исчерпании попыток (5 попыток за ~10 часов) запись переходит в статус failed. Необходим мониторинг таблицы webhook_deliveries на накопление failed записей — сигнал о системной проблеме на стороне мерчанта.
