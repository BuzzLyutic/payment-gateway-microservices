# ADR-004: Fail-open стратегия Risk Service при недоступности Redis

## Статус
Accepted

## Контекст

Risk Service оценивает каждую транзакцию по двум типам правил:

**Simple-правила** — сравнение полей транзакции с пороговыми значениями. Не требуют внешних зависимостей: `amount > 300000`, `hour between [1, 5]`.

**Velocity-правила** — подсчёт частоты событий за скользящее временное окно через Redis INCR + TTL. Требуют доступности Redis: `более 5 транзакций от одного мерчанта за 10 минут`.

Redis — единственная внешняя зависимость Risk Service в части velocity-проверок. При его недоступности необходимо выбрать поведение системы:

- **Fail-closed**: блокировать все транзакции до восстановления Redis
- **Fail-open**: пропускать транзакции, применяя только simple-правила

Платёжная платформа обслуживает коммерческих мерчантов. Недоступность обработки платежей влечёт прямые финансовые потери мерчантов и репутационный ущерб платформы.

## Решение

Принята стратегия **fail-open**: при недоступности Redis velocity-проверки пропускаются, simple-правила продолжают работать. Транзакции не блокируются из-за недоступности вспомогательного хранилища.

Реализация: если velocity-проверка возвращает ошибку `domain.ErrRedisUnavailable` — правило считается не сработавшим, его score не добавляется к итоговому риск-скору. 
Simple-правила выполняются независимо.

```go
// fail-open: velocity-правило пропускается, simple-правила продолжают работать
if isRedisUnavailable(err) {
    return false, domain.ErrRedisUnavailable
}
```

## Обоснование выбора
Изначально рассматривался fail-closed как более консервативный подход. Анализ последствий показал, что fail-closed создаёт гарантированный ущерб, тогда как fail-open создаёт вероятностный риск.

### Асимметрия потерь:

Fail-closed при outage Redis гарантированно блокирует 100% легитимных транзакций на всё время недоступности. Это прямые потери мерчантов, недовольство пользователей, репутационный ущерб платформы — и всё это с вероятностью 1.

Fail-open допускает риск пропуска мошеннических транзакций с вероятностью значительно меньше 1. Вероятность скоординированной атаки именно в момент outage Redis ненулевая, но существенно ниже гарантированного ущерба от полной блокировки.

### Velocity — один из нескольких слоёв защиты:

При fail-open продолжают работать:

- Simple-правила Risk Service (сумма, время суток)
- Circuit Breaker на провайдерах
- Idempotency key — защита от дублей
- Fraud-системы самих платёжных провайдеров
- Ручной мониторинг и алертинг

Velocity-проверки усиливают защиту, но не являются единственным барьером. Атакующий в любом случае проходит через несколько независимых слоёв.

### Временной фактор:

Redis — in-memory хранилище с высокой доступностью. Типичная продолжительность outage: секунды — единицы минут. За это время через пропущенные velocity-проверки может пройти ограниченное число транзакций.

### Отраслевая практика:

Крупные платёжные процессоры (Stripe, Adyen) используют многоуровневую защиту именно потому что ни один слой не является абсолютным барьером. Полная блокировка обработки из-за недоступности вспомогательного компонента противоречит принципам построения отказоустойчивых платёжных систем.

## Альтернативы

### Fail-closed: блокировать все транзакции при недоступности Redis

Максимально консервативный подход. Ни одна транзакция не пройдёт без полной проверки рисков.

Отвергнут: создаёт гарантированный ущерб с вероятностью 1 при любом outage Redis — включая плановые рестарты, сетевые флюктуации, кратковременные перегрузки. Недоступность платёжной платформы критичнее временного ослабления одного слоя защиты.

### Fail-closed только для velocity, fail-open для остальных

Семантически совпадает с принятым решением, так как simple-правила не зависят от Redis. Формулировка избыточна.

### Кэширование счётчиков в памяти при недоступности Redis

In-memory fallback: хранить velocity-счётчики локально при сбое Redis. Даёт velocity-проверки даже при недоступности Redis.

Отвергнут: при нескольких инстансах сервиса in-memory счётчики не синхронизированы между подами — атакующий может распределить запросы по инстансам и обойти лимиты. Создаёт иллюзию защиты вместо реальной. Усложняет код без надёжного результата.

### Circuit Breaker на Redis соединении

Отдельный Circuit Breaker для Redis, который при открытии переключает в fail-open режим. Добавляет явное управление состоянием.

Не реализован как отдельный компонент — текущая реализация через проверку типа ошибки isRedisUnavailable(err) даёт тот же результат проще. При необходимости метрик по состоянию Redis-соединения Circuit Breaker стоит рассмотреть.

## Последствия

### Стало лучше:

Платформа сохраняет работоспособность при кратковременных сбоях Redis. Simple-правила продолжают фильтровать очевидно подозрительные транзакции (крупные суммы, ночное время). Остальные слои защиты функционируют без изменений.

### Принятые риски:

В период недоступности Redis velocity-проверки не работают. Если в это время произойдёт атака типа card testing (множество мелких транзакций для проверки карт) — часть из них может пройти проверку рисков. Провайдеры и их fraud-системы остаются последним барьером.

### Необходимые компенсирующие меры:

- Мониторинг и алертинг на недоступность Redis — outage должен быть замечен немедленно, не через жалобы пользователей 
- Логирование каждого случая пропуска velocity-проверки для последующего аудита
- Минимизация времени восстановления Redis: persistent storage, healthcheck с быстрым rescheduling в оркестраторе
